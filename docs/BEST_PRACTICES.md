# Best Practices

Guidelines for writing fast, correct, and maintainable code in **vcsr**. vcsr
targets the [vanilla](https://github.com/enghitalo/vanilla) ecosystem, so it
follows the same three rules (from vanilla's
[CONTRIBUTING](https://github.com/enghitalo/vanilla/blob/main/CONTRIBUTING.md)):

> 1. Don't slow down performance.
> 2. Always keep abstraction to a minimum.
> 3. Don't complicate it.

…plus the one rule that defines this project:

> 0. **Never modify the V compiler.** vcsr is a source generator that emits plain
>    V; the stock `v` compiles it. See [ARCHITECTURE.md](ARCHITECTURE.md).

Everything below is a concrete way to honor those rules.

---

## 1. Compiler passes are pure functions

Each phase is a **total function of `input -> output`**. It must not read globals,
do hidden I/O, or mutate shared state. File reading happens once at the edges
(the CLI); the passes work on values.

```v
parser.parse_template(src string) !ast.Tree     // phase 01
slots.compile(tree ast.Tree) !CompiledTemplate  // phase 02
```

**Do**

- Treat the AST / IR as immutable input; return a new value.
- Keep file I/O in the CLI layer, not inside `parse_*`/`compile`/`codegen`.
- Make a pass independently testable (feed a string/AST, assert the result) —
  that's exactly what the [`tests/`](../tests) phase specs do.

**Don't**

- Read a file from inside a pass.
- Stash state in a package-level `mut` variable between calls.
- Reach across phases — phase N consumes only phase N-1's output.

---

## 2. Stay zero-copy: slice the source, don't copy it

The parser works over the original template string. Reach for the bytes you
already have before allocating new ones.

**Do**

- Slice the source (`p.src[start..p.pos]`) for tag names, attribute values, and
  text runs — this preserves UTF-8 and allocates nothing extra.
- Defer `.clone()` only when a value must outlive the source buffer.

**Don't**

- Append the source byte-by-byte to build a token (`buf += c.ascii_str()`) — it
  reallocates and breaks multibyte characters. Track a start index and slice.
- Copy the whole template to inspect a few characters.

---

## 3. Avoid `${}` interpolation on the codegen hot path

String interpolation (`'… ${x} …'`) is **not free in V**: it allocates a new
`string`, and for non-string values it first calls `.str()` — another allocation.
Codegen emits a lot of V source text per component, so that overhead is real.

### 3a. Static fragments → `const`

Boilerplate that never changes (import lines, function signatures, runtime call
names) should be string `const`s, written verbatim.

```v
const gen_header = '// GENERATED by vcsr. Do not edit.\nimport vcsr.runtime\n'
```

### 3b. Dynamic output → pre-sized builder, parts written separately

```v
fn emit_view(ct CompiledTemplate) string {
    mut sb := strings.new_builder(256 + ct.html.len)
    sb.write_string("\tmut ins := __tpl.instance()\n")
    for i, s in ct.slots {
        sb.write_string('\tbind_')
        sb.write_string(s.kind.str())   // small, known set
        sb.write_string('(ins, ')
        sb.write_decimal(i)             // no .str(), no alloc
        sb.write_string(')\n')
    }
    return sb.str()
}
```

Compare the slow form — every `${}` allocates:

```v
// DON'T: hidden allocations per slot
sb.write_string('\tbind_${s.kind}(ins, ${i})\n')
```

**Do**

- Precompute fixed fragments as `const`.
- Use `write_decimal` (ints), `write_u8` (single bytes), `write_string` (literals).
- Seed the builder with a realistic estimate (`base + ct.html.len`).

**Don't**

- Use `${}` to assemble generated lines on the hot path.
- Call `.str()` just to concatenate — `write_decimal` avoids it.

> `${}` is fine **off** the hot path — in `eprintln`/`error()` for diagnostics,
> where readability beats the one-time allocation.

---

## 4. Allocate with intent

See [V_PERF_TOOLBOX.md](V_PERF_TOOLBOX.md). Key points:

- `[]u8{cap: n}` is uninitialized/noscan; `[]u8{len: n}` is zeroed — pick the
  `cap` form when you'll overwrite the bytes anyway.
- A large `cap` adds GC pressure; size to the realistic template, not the worst
  case, and reuse a buffer across a compile where lifetimes allow.

---

## 5. Emit plain V — no compiler magic, ever

The output of codegen (`*.gen.v`) must compile with an **unmodified** `v`.

**Do**

- Generate ordinary V that `import`s only `vcsr.runtime`.
- Keep all "magic" in vcsr's own parsers/codegen, where it's plain code.

**Don't**

- Emit `$vui`, `$css`, or any `$`-builtin — those would require forking V. The
  phase-04 spec asserts the generated source contains none.
- Depend on a patched V, a custom comptime function, or a V plugin.

---

## 6. Output must be deterministic and cacheable

The build content-hashes assets, so identical input must yield byte-identical
output.

**Do**

- Keep skeletons stable: the same markup → the same `CompiledTemplate.html`
  regardless of the driving expressions (a phase-02 invariant, already tested).
- Order slots and emitted declarations deterministically (document order).

**Don't**

- Use `Date.now()` / randomness / map-iteration order in codegen — it breaks
  hashing and reproducible builds. Intern by content, not by insertion time.

---

## 7. Generated code is safe by construction

vcsr controls how values reach the DOM, so it must not generate injection bugs.

**Do**

- Bind text via `textContent` (the phase-02 `text` slot), never by building an
  HTML string from a runtime value.
- Escape per context for attribute/URL slots; treat every interpolated value as
  untrusted unless explicitly marked raw.

**Don't**

- Generate `innerHTML = <user value>` from an interpolation.
- Emit a value into a `<script>`/URL/style context without context-aware escaping.

---

## 8. Test each phase without the full pipeline

Passes are pure, so each phase is tested in isolation by feeding it input and
asserting on the output value.

**Do**

- Add/extend the phase spec in [`tests/`](../tests) (e.g.
  `phase_01_template_parser_test.v`) and keep it green.
- Cover malformed input (unclosed tags, mismatched closes, malformed `@for`) and
  edge cases (UTF-8 text, escaped `{{{{`), not just the happy path.
- Run `v fmt -verify` on changed files.

```sh
ln -s "$PWD" ~/.vmodules/vcsr        # make `import vcsr.*` resolve
v test tests/phase_01_template_parser_test.v
```

---

## 9. Benchmark codegen before and after perf changes

Performance claims must be measured, not assumed.

**Do**

- Build with `-prod` and time the compiler over a large, realistic template set
  (many components, deep trees, big lists).
- Prefer A/B comparisons; report more than one run.

**Don't**

- Compare a `-prod` build against a debug build.

---

## 10. Follow the project conventions

- A component is the `name.v` / `name.html` / `name.css` **triplet**
  ([ARCHITECTURE.md](ARCHITECTURE.md)); don't reintroduce inline template/style
  strings.
- `*.gen.v` is **generated** — never hand-edit it; regenerate from the source.
- No new abstraction layer that wasn't strictly necessary (rule 2).

---

## Checklist before opening a PR

- [ ] Each pass stays a pure `input -> output` function; no hidden I/O.
- [ ] Generated code is plain V (no `$`-builtins) and imports only the runtime.
- [ ] Output is deterministic (stable skeletons, document-order slots).
- [ ] Hot-path codegen avoids `${}`; uses a pre-sized builder.
- [ ] Generated DOM bindings are injection-safe by construction.
- [ ] Tests added/updated and green; `v fmt -verify` clean.
- [ ] Benchmark shows no regression for perf-sensitive changes.
- [ ] No new abstraction layer that wasn't strictly necessary.
