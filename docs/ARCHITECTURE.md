# Architecture: a standalone compiler, no V changes

A hard constraint shapes this whole project: **vcsr must not modify the V
compiler or its repository.** That rules out language-level magic like comptime
builtins (`$vui`, `$css`). Instead, vcsr is a **standalone source generator**
that runs *before* `v`, with its own parsers, and emits **plain V** that the
stock V compiler turns into WASM.

```
  your sources                vcsr (standalone)                stock toolchain
  ────────────                ─────────────────                ───────────────
  counter.v   (logic)   ┐
  counter.html (template)├──▶  parse .html + .css   ──▶  counter.gen.v  ──▶  v -cc clang ──▶  *.wasm
  counter.css (styles)  ┘     resolve refs, codegen      (plain V)            (→ WASI SDK)
```

Nothing in this pipeline patches V. vcsr is "just" a code generator + a runtime
library written in ordinary V.

> **On the compile step.** The "stock toolchain" box is `v -cc clang` feeding the
> [WASI SDK](https://github.com/WebAssembly/wasi-sdk) (`clang --target=wasm32-wasip1`),
> **not** `v -b wasm`. As of V `130caaf` (2026-06), the native `-b wasm` backend
> still can't compile the runtime — `vlib/v/gen/wasm/gen.v` errors `wasm backend
> does not support dynamic arrays`, and its browser DOM interop is `fn JS.*`
> passing `(ptr,len)` through linear memory, not `externref`. The C→clang route
> compiles V's full language + stdlib (with `-gc none` + a small WASI shim). The
> wasm *interface* vcsr targets — and which producer/toolchain may change over
> time — is pinned in [WASM-ABI.md](WASM-ABI.md); all three V→WASM routes are
> measured feature-by-feature in [WASM-PATHS-ANALYSIS.md](WASM-PATHS-ANALYSIS.md).

## Why not `$vui` / `$css`?

Those would have to be **compiler builtins** (comptime functions baked into V),
which means changing the V repository. We won't. So templates and styles can't
be magic strings the compiler understands — they are **separate files** that
*vcsr's own parsers* read, exactly the parsers the phase-01/02/05 specs describe.
This is strictly better for the goal: the V toolchain stays untouched and
upgradable, and the template/style languages evolve in vcsr, not in V.

## Components are a file triplet (by basename)

A component is up to three co-located files sharing a basename:

```
counter/
├── counter.v      # @[component] struct + state (signals) + handlers/lifecycle
├── counter.html   # the template (vcsr's HTML dialect)
└── counter.css    # scoped styles (optional)
```

- `counter.v` holds only **logic**: the `@[component]` struct, its signal
  fields, event handlers, and lifecycle hooks (`on_mount`, …). It does **not**
  contain `view()` or `style()` — vcsr generates those.
- `counter.html` is the template. Identifiers in it resolve in the component's
  scope: `{{ count }}` reads the struct's `count` field; `@click="inc"` binds the
  struct's `inc` method.
- `counter.css` is plain CSS; vcsr scopes it to the component at build time.

`@[component]` is an ordinary V struct attribute (no compiler support needed);
vcsr discovers components by scanning sources for it, then pairs each with the
same-basename `.html`/`.css`.

## The template dialect (parsed by vcsr, not V)

| Feature | Syntax (in `.html`) |
|---|---|
| Interpolation | `{{ expr }}` |
| Event | `@click="handler"` / `@click="count.set(0)"`, modifiers `@submit.prevent` |
| Two-way bind | `@bind="signal"` |
| Conditional | `@if="cond"` |
| List | `@for="item in items"` + `:key="item.id"` |
| Dynamic class | `class:done="item.done"` |
| Static prop | `<Button label="ok" />` |
| Bound prop | `<Button :label="name" @click="inc" />` |

All identifiers resolve against the component struct (the implicit `self`). vcsr
type-checks them against the struct's fields/methods at build time; an unknown
reference or a wrong type is a build error.

## What vcsr generates (plain V, no builtins)

For `counter.v` + `counter.html` + `counter.css`, vcsr emits `counter.gen.v` in
the same module:

```v
// counter.gen.v — GENERATED by vcsr. Do not edit. Plain V; imports only runtime.
module main

import vcsr.runtime { Template, SlotDesc, SlotKind, bind_text, bind_event }

const __counter_tpl = Template{
	html:  '<main class="counter_x1"><h1></h1><p class="muted_x1"></p><button>+1</button></main>'
	slots: [
		SlotDesc{ kind: .text,  path: [0] },
		SlotDesc{ kind: .text,  path: [1] },
		SlotDesc{ kind: .event, path: [2], name: 'click' },
	]
}

pub fn (mut c Counter) view() vcsr.View {
	mut ins := __counter_tpl.instance()
	bind_text(ins, 0, fn [c] () string { return c.count.get().str() })
	bind_text(ins, 1, fn [c] () string { return (c.count.get() * 2).str() })
	bind_event(ins, 2, c.inc)
	return ins.view()
}

pub fn (c Counter) style() string {
	return '.counter_x1{display:grid;gap:.5rem}.muted_x1{color:var(--muted,#888)}'
}
```

Key properties the phase-04 spec pins down:

- The generated file is **plain V**: it contains no `$vui`, no `$css`, no
  compiler builtins — only normal V plus an `import` of the vcsr runtime library.
- The runtime (`vcsr.runtime`) is itself plain V built on the minimal `js` FFI
  substrate (host handles via `externref`); see [DESIGN.md](DESIGN.md).
- The embedded HTML skeleton + slot table is exactly the clone-and-patch model
  from [DESIGN.md](DESIGN.md) — registered once as a native `<template>`, cloned
  per instance, slots patched by signals.

## Build flow

```sh
vcsr build ./src --out dist     # 1) scan .v for @[component], pair with .html/.css
                                # 2) parse templates/styles, type-check refs
                                # 3) emit *.gen.v (plain V) + scoped app.css
                                # 4) invoke stock `v` (v -cc clang → WASI SDK) to compile .v + .gen.v → wasm
                                # 5) bundle: hashing, brotli, manifest (phases 08–10)
```

Steps 1–3 are pure vcsr (parsers + codegen). Step 4 shells out to an
**unmodified** `v`. That separation is the whole point: vcsr can do everything a
modern frontend compiler does without a single change to the V language.

## Consequences

- **No V fork to maintain.** Upgrade V freely; vcsr only depends on the stock
  `v` accepting normal V and emitting wasm — today the `v -cc clang` + WASI SDK
  path (the native `-b wasm` backend isn't ready; see the note above and
  [WASM-ABI.md](WASM-ABI.md)).
- **`.html`/`.css` get real tooling.** Because they're real files in known
  languages, editors give syntax highlighting, formatters, and linters for free —
  something inline `$vui('…')` strings never get.
- **The dialect evolves in vcsr.** New template features ship in the vcsr parser,
  not in a V release.
- **Codegen is inspectable.** `*.gen.v` is readable plain V you can open, diff,
  and debug (with source maps back to the `.html`).
