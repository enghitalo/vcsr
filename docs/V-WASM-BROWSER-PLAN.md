# Making `v -b wasm -os browser` production-ready for vcsr

> Engineering plan. Verified against `/home/hitalo/v/vlib/wasm`, `/home/hitalo/v/vlib/v/gen/wasm`, and the vcsr tree on 2026-06-21. Confirmed by direct grep: `module.v:11/16` declare `table_section`/`element_section` ids with **no `assign_table`, no `elements` field, and no encoder**; `ref_func` (0xD2) exists at `instructions.v:1203` but there is **no `call_indirect`, no `0xfb` GC op, no table/elem writer**; `wasm-opt` runs **only under `-prod`** as the unconstrained `-all -lmu -c -O4` (`gen.v:1875`); `is_pure_type` is consulted at **~13 sites** in `mem.v` (160/261/362/371/422/442/473/509/801, …) — not just the FFI gate; **both** option _and_ result are hard-errored (`gen.v:240/259/265`); vcsr ships `-Wl,--export-all` (`cmd/vcsr/vcsr.v:124`) and `wasm/wasm.v` already models `DomAbi.externref` as the **target** while shipping the integer-handle bridge.

> **Browser-targeting posture.** This plan targets **evergreen and future browsers** — current Chrome / Firefox / Safari and beyond — not legacy versions. Every "Safari floor" reference below means _current_ Safari (18.x, 2024–2025), which already ships reference-types, WasmGC, tail calls, and exnref; it is a **modern baseline, not a conservative one**. The default `-os browser` feature set is therefore free to **adopt the advanced WASM features the current baseline supports** (externref + funcref tables now; WasmGC, tail calls, and exnref EH as the emitter reaches them). The only things kept behind feature-detect are features _not yet shipped across the current baseline_ — JS String Builtins on Safari, JSPI, Memory64 on Safari — and those are **optional fast-paths, never blockers**. Where this plan _defers_ a feature (notably WasmGC to P6), the driver is **emitter effort, not browser support**.

## 1. Executive summary & strategic thesis

vcsr is a fine-grained reactive web framework whose browser path compiles V to WebAssembly. There are two compile paths, and **they sit at opposite ends of every curve that matters**:

|                     | **Path 2 — `v -cc clang` + wasi-sdk** (ships today)                                           | **Native `v -b wasm -os browser`** (the endgame)                                                |
| ------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Language coverage   | Full V — _but_ capturing closures and `map[string]V` **validate then trap at runtime**        | Scalar + structs + fixed arrays today; **everything else ICEs**                                 |
| Counter `core.wasm` | 165 KB raw / **56 KB brotli**, 45 WASI imports, 558 exports                                   | trivial module **2 KB → 205 B brotli**, 2 imports, ~6 exports                                   |
| DOM boundary        | integer handle table + JS-side `Map` (forced by LLVM #141011: externref can't persist from C) | **externref-native** — DOM nodes as first-class refs                                            |
| Closures            | runtime-generated exec memory → wasm W^X trap                                                 | vcsr's explicit **`(fnidx, ctx ptr)` pairs** become funcref table entries (legal, type-checked) |
| Memory              | libc malloc in linear memory                                                                  | shadow stack today → TLSF, then **host WasmGC**                                                 |
| Toolchain           | V→C→clang, `WASI_SDK` dependency, 2-step                                                      | single command, no clang, no wasi-sdk                                                           |

**The thesis: the native backend is the endgame, and the migration off clang is itself the single largest hardening, size, and capability win.** The clang path is at its size floor (`wasm-opt -Oz` recovers <1%) and is _structurally_ incapable of three things vcsr needs — externref-persisted DOM, callable function values without W^X exec memory, and a tracing GC for its cyclic `Signal⇄Effect` graph. The hand-written native emitter can emit all three because it writes wasm bytes directly, not through a C compiler.

**The binding constraint is the emitter, not the browser.** The Safari floor (reference-types 15, WasmGC 18.2, tail calls 18.2, exnref 18.4) is met for every feature vcsr would _enable_, but each feature is opt-in and the **default `-os browser` set must pass T3 on the Safari floor unaided** (§6). The gap is that V's ~4.5k-LOC byte emitter has **no `call_indirect`, no table/elem writer, and zero GC opcodes**. The early phases (P1–P5) are largely _additive emitter work on a known-good substrate_ — the struct/fixed-array layout engine and `serialise` pool already work and are reused by every feature. **WasmGC (P6) is the exception: it is a second, parallel memory model — effectively a second backend — and is not "additive on the known-good substrate."** Effort is honest about that below.

**The good news vcsr brings:** its runtime is already shaped for this backend. It is **closure-free by construction** — every reactive primitive is a top-level `fn (ctx voidptr)` plus a `voidptr` ctx in an `@[heap]` struct, invoked as `b.get(b.ctx)` / `h.run(h.ctx)`. So the highest-leverage missing feature is not general V closures (which capture an environment and _cannot_ be lowered to a bare funcref) — it is **calling a function value stored in a struct field**: `ref.func` → table index → `call_indirect`. That one capability unlocks vcsr's entire reactive core. **The plan does not claim general V closure support from this work.**

**The single highest-leverage first move** is P0-HARNESS+P2 sequencing: stand up the four-tier conformance gate, then deliver the table/element-section writer and `call_indirect` (P2). Everything reactive depends on it, and — per the critical fix below — even the `ref.func` that "works today" does not actually _validate_ without an element segment.

## Special focus — where the clang paths (Path 1 & Path 2) fall short

vcsr ships today on **Path 2 (V → C → clang/wasi-sdk → wasm)**. **Path 1 (pure clang → wasm)** is the language-neutral ceiling reachable from V via C-interop. Both were empirically measured on this machine (2026-06-21; wasi-sdk 25/LLVM19 _and_ 33/LLVM22 — identical; V 0.5.1; Node 26/V8). The decisive finding: **`wasm-validate` passing is not proof of execution** — a capturing closure and a `map[string]V` both validate cleanly and then trap or silently corrupt at runtime. The walls below are **toolchain-structural** (LLVM/clang cannot emit the needed shapes), not effort gaps that more glue closes. Only a native `-b wasm` backend that _owns codegen_ escapes them.

| Axis                      | Path 1 (pure clang)                                           | Path 2 (V → clang)                                                            | Native `-b wasm` (target)                                     |
| ------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Capturing closures        | ❌ no source lang; exec-memory model forbidden by wasm anyway | ❌ TRAP: `RuntimeError: table index is out of bounds` (lowered to exec pages) | ✅ funcref table entry + captured-env struct — runs           |
| String-keyed maps         | ⚠️ hand-roll in C                                             | ❌ silent corruption: `m['a']`→0; later `Probe overflow` panic                | ✅ correct wasm map (or WasmGC)                               |
| externref DOM persistence | ❌ LLVM #141011: global/struct/table store fails              | ❌ same #141011 → forced onto i32 handle table                                | ✅ DOM nodes as first-class externref in tables / GC structs  |
| WasmGC / type-safe heap   | ❌ no clang WasmGC producer                                   | ❌ no clang WasmGC producer                                                   | ✅ engine-traced, type-safe heap objects                      |
| WASI ambient surface      | ⚠️ only via `-nostdlib` + hand C                              | ❌ ~45 `wasi_snapshot_preview1` imports → mandatory JS shim                   | ✅ **zero WASI** on `-os browser`; only explicit host imports |
| Binary-size floor         | ⚠️ libc floor unless `-nostdlib`                              | ❌ ~64 KB (V runtime + libc) before app code                                  | ✅ no libc floor; host-GC offload                             |
| Host-call indirection     | ❌ externref non-persist → i32→`Map` per op                   | ❌ same handle-table indirection per DOM op                                   | ✅ direct externref — no side table                           |
| "validate ≠ run" risk     | ⚠️ C semantics; no V-level traps                              | ❌ **HIGH**: closures/maps validate then trap silently                        | ✅ codegen owns semantics — validation tracks execution       |

### Memory

**Path 1/2 shortfall.** clang emits **linear-memory only**: all heap state is raw pointer arithmetic, no type-safe references. `-gc none` leaks unless manually freed; there is **no WasmGC producer in clang** to offload to the host collector. The externref non-persistence wall (**LLVM #141011** — storing externref in a global/struct/array/table yields `cannot select … store` / `field has sizeless type` / `only zero-length tables`) forces every host/DOM reference into a **manual i32 handle table** indexing a JS `Map` — leak-prone and **invisible to both GCs**. **Native:** target WasmGC for host-GC'd, type-safe, compact objects — no pointer arithmetic for refs, no manual handle table.

### Performance

**Path 1/2 shortfall.** Every DOM/host op pays **handle-table indirection** (i32→`Map` lookup) instead of a direct externref dereference; the mandatory **WASI shim** interposes an extra JS call layer; the absence of externref forces extra boundary marshalling. **Native:** DOM nodes are first-class externref — host calls pass the reference directly, no i32→Map hop, no shim layer.

### Security

**Path 1/2 shortfall.** Path 2 imports **~45 `wasi_snapshot_preview1` functions** (fs/clock/random stubs) — ambient authority a browser target should never request, present purely because the toolchain links libc. The **linear-memory model** permits in-module pointer corruption with no type-safe heap. The **handle table is forgeable from the guest**: any i32 is a candidate index into the host `Map`. **Native:** emits **zero WASI** on `-os browser` (only declared host imports), and WasmGC references are type-safe and unforgeable.

### Size

**Path 1/2 shortfall.** A **~64 KB uncompressed floor** (V runtime + libc) before any app code, plus a bundled allocator/GC in linear memory, with no host-GC offload. `wasm-opt -Oz` on the clang counter recovers **< 1%** — the clang path is at its floor. **Native:** drops the libc floor, offloads collection to the host GC; baseline becomes the app's own code.

### DOM (the framework-defining wall)

**Path 1/2 shortfall.** Because of **#141011**, externref works as a param/local/return but **cannot persist** in a global, struct, array, or table — so a DOM framework **cannot cache a node as a first-class wasm reference** and is forced onto the **i32 handle table** with per-op indirection. The DOM is the substrate of the whole framework; modeling every node as a forgeable integer with a side-table lookup is a structural defect, not a tuning problem. **Native:** DOM nodes live as **externref in tables / WasmGC structs** directly.

### Language features

**Path 1/2 shortfall.**

- **Capturing closures TRAP.** V lowers `fn [x] () {...}` to runtime-generated **executable memory** (mprotect/exec pages, `vlib/builtin/closure/closure_nix.c.v`); wasm forbids runtime code generation → `RuntimeError: table index is out of bounds`. Non-capturing fn values work. This kills any closure-based reactive runtime.
- **String-keyed maps are broken.** `m['a']=7; m['a']`→`0`; `'a' in m`→`false`; `m.len` correct; a 2nd op panics `Probe overflow`. `map[int]int` works and `hash.sum64_string` is deterministic — it's V's **string-key clone/equality** path on wasm, not wyhash.
- **Hidden init.** Must call `_vinit(0,0)` after `_initialize()` (V registers global init as a C constructor only on `_WIN32`) or the first map/string op panics `division by zero`.
- **`fn C.foo` emits no prototype** → clang `call to undeclared function` unless you hand-author a header with `import_module`/`import_name`.
- **Advanced features are C-only.** Threads/SIMD/EH/tail-calls are reachable only as hand-written C + linker flags, none exposed through V's frontend. relaxed-SIMD: LLVM emits it but bundled binaryen rejects the opcodes. Component Model: needs a WASI adapter and no browser runs it.

**Native:** lowers capturing closures to **funcref table entry + env struct** (no exec memory — they run), emits a **correct wasm map** (or WasmGC), and exposes wasm features through V's own frontend.

### Hard walls only the native backend clears

Impossible on clang — toolchain-structural, not closable with glue:

- **Closures that actually run** — wasm forbids the exec-memory model; only codegen that lowers to funcref-table + env-struct produces running closures.
- **Persisting a DOM node as a first-class wasm reference** — LLVM **#141011** blocks externref storage for _any_ clang output; the handle table is the only option on clang.
- **A WasmGC, host-GC'd, type-safe heap** — clang has **no WasmGC producer** at all.
- **Zero ambient WASI on the browser target** — clang/wasi-sdk links the ~45-import surface; only an import-owning backend emits none.
- **Dropping the ~64 KB libc floor** — inherent to linking libc through C.
- **Validation that implies execution** — only codegen ownership makes a passing `wasm-validate` mean the program runs.

## 2. Current state — what works, what ICEs (verified)

### What the native backend does today

- i32/i64/f32/f64 arithmetic, comparisons, bitwise/shift; structured control flow (`if/loop/block/br*`); `load*/store*`; `local_*`/`global_*`.
- Named structs and `[N]T` fixed arrays, lowered to an **i32 pointer into a stack frame**, with correct field offsets via the `serialise` pool. **This is the reusable layout engine.**
- Direct `call` / `call_import`; `match`, `for-in-range`, string concat (`+`); `$if` comptime; inline `asm wasm` (which itself hand-emits `memory.grow`/`ref.null`/`call_import` — see R-ASM).
- `ref.func` / `ref.null` / `ref.is_null` opcodes exist (`instructions.v:1189/1200/1203`); `funcref_t`/`externref_t`/`v128_t` are _typed_ in `ValType`/`RefType`. **CAVEAT (critical):** an emitted `ref.func N` only _validates_ if `N` is reachable via a declarative/active element segment, an export, a table, or a global. With no element-section writer, today's `ref.func` validates **only by accident** when the target fn happens to be exported. This is a latent validation blocker, not a working feature (see P2-EMIT).
- `pub` main-mod fns auto-export under `-os browser`/`-os wasi` (`gen.v:288`).
- A real `start` section (`assign_start('_vinit')`) — the native browser module can boot with **zero JS glue**.
- `memory.copy`/`fill`/`grow`/`size` opcodes exist in `vlib/wasm` (but `memory.grow` is never called from generated code).

## 3. Target architecture

```
                         ┌──────────────────── BROWSER TAB ────────────────────┐
  loader_native.js  ──▶  │  WebAssembly.instantiateStreaming(core.wasm)         │
  (~15 LoC DOM bridge,    │  start=_vinit  •  imports: env.{dom_*} externref    │
   no WASI, no H[] map)   │                                                     │
                          │   ┌─ VALUES (strings, numbers) ──▶ linear memory ─┐ │
  DOM node ─ externref ─▶ │   │  TLSF heap [__heap_base, __vsp)               │ │
  click   ─ funcref   ◀── │   │     []T  •  map[K]V  •  sum  •  ?T/!T         │ │
                          │   └──────────────────────────────────────────────┘ │
                          │   ┌─ IDENTITIES (DOM nodes, callbacks) ───────────┐ │
                          │   │  externref in an externref TABLE (sizeless —   │ │
                          │   │    NEVER in linear memory) ── table.get/set    │ │
                          │   │  funcref table entries  ──▶ call_indirect      │ │
                          │   └────────────────────────────────────────────── ┘ │
                          │   (Phase 4+) WasmGC heap: Signal[T]/[]T/maps as      │
                          │      engine-traced struct/array; externref in GC     │
                          │      array fields → cyclic graph collected, *if*     │
                          │      the host JS side also drops its reference        │
                          └───────────────────────────────────────────────────┘
```

**Three architectural commitments:**

1. **Values vs identities split.** Strings/numbers travel in linear memory (`ptr,len`, or JS-string-builtin externref only where feature-detected). DOM nodes and host callbacks **never enter linear memory** — they are externref/funcref, held on the stack, in **dedicated reference tables**, and (Phase 4 GC, P6) in WasmGC fields. This is the security capability model: the guest can only hold references the host handed it; it cannot forge a node from an integer.

2. **Function-values-as-funcref, never exec memory.** vcsr's `fn(ctx voidptr)+voidptr` ABI lowers to `(table index i32, ctx ptr)`; calling a stored handler is `call_indirect`. This is exactly what wasm allows and clang cannot. **It does not generalize to capturing V closures** (those need a captured environment) — vcsr is closure-free by construction, so this is sufficient _for vcsr_.

3. **Two memory models, sequenced not forked.** Linear-memory **TLSF** allocator first (ships the reactive core fastest); **WasmGC behind `-d wasm_gc` much later (P6)** for the cyclic `Signal⇄Effect` graph, externref-in-GC-fields DOM, and data-segment elimination. **Do not split foundational effort across both.** Because externref is sizeless and cannot live in linear memory, the Phase-A (pre-GC) DOM-slot storage is an **externref table**, not a GC array — P2 must deliver that table (incl. `table.grow` on externref).

## 4. The single phased roadmap (P0 → P6)

Ordering resolves all cross-lane dependencies: **harness → allocator → dyn arrays → (table/elem writer + call_indirect, the keystone) → generics → interfaces → externref DOM → maps/sum/opt-result → WasmGC → advanced.** Two independent spines run in parallel inside the early phases:

```
SPINE A (memory):  heap ──▶ []T ──┬─▶ maps ──▶ parser native (needs string-method surface)
                                  ├─▶ sum types ──▶ AST variants
                                  └─▶ ?T/!T ──▶ idiomatic errors
SPINE B (calls):   table/elem writer + call_indirect ──┬─▶ generics (Signal[T]) ──▶ interfaces (Component)
                                                       ├─▶ reactive core (effects/dispatch)
                                                       └─▶ externref DOM + event funcrefs
```

Effort: S/M/L/XL. Risk: low/med/high. Every milestone's acceptance is **compile AND run** (T0 compile → T1 `wasm-validate` → T2 execute-in-Node26/V8 → T3 Chromium). **"Validates but traps" is a hard FAIL** — the lesson of Path 2. **All size/DCE acceptance figures assume a `-prod` build** (the only path that runs `wasm-opt`); non-`-prod` builds are larger and are not gated on size.

### P2 — Table/element writer + `call_indirect` (Spine B root) — **THE keystone**

## 5. Cross-cutting concerns

### 5.1 Memory

| Decision                             | Choice                                                             | Rationale                                                                                                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Frontend contract                    | `-gc none`, autofree off, manual `dispose()` only (P0-AUTOFREE)    | prevents frontend-inserted frees colliding with `__v_free`                                                                                                                                           |
| Phase-A allocator                    | **TLSF free-list** (~3 KB code), not bump-only                     | per-render alloc≈free; bump leaks. | Growth                               | `memory.grow` + collision guard vs `__vsp`                         | the two regions grow toward each other unguarded today.                                                                                                                                              |

| Phase-B target                       | **WasmGC** (`-d wasm_gc`, Safari18.2 floor)                        | the `Signal⇄Effect` graph is _inherently cyclic_ — refcounting provably leaks it; a tracing host GC collects it (when both sides drop). Clang counter section breakdown: code 67.4%, data 22.4%, **export 8.3% (the `--export-all` bug)**, WASI imports 1.1%. `wasm-opt -Oz` on the clang module recovers only −0.9% — **the clang path is at its floor; the only clang win is killing `--export-all` (P0-SZ-EXPORT). Everything else requires the native backend.** Native size levers: zero WASI, no bundled allocator until needed, closed-world DCE via binaryen `-c` (requires `-prod`), `-Oz` over `-O4`, WasmGC deletes data-segment string/type tables, externref deletes the handle-table data + marshalling, MAIN/SIDE code-split ships only the delta. **Only the trivial-module figure is a CI gate; runtime-bearing figures are tracked, not gated.**

## Bottom line

Realistic sequencing is **not** "many parallel L milestones" — it is one keystone gating a long additive tail, with one genuinely large second-backend at the end. Stand up the four-tier conformance harness (P0-HARNESS) and immediately fix the two cheap, high-value toolchain bugs (`--export-all` → allowlist; `wasm-opt -all` → floor-safe `--enable` allowlist with post-opt re-validate), then deliver the **table/element-section writer + `call_indirect` (P2)** — including the easily-missed **declarative element segment** without which even today's `ref.func` does not validate, and a **single elem-segment owner** that P3-IFACE and P4-EVT later share. That one capability turns vcsr's closure-free `(fnidx, ctx)` reactive core from un-compilable to running, and it is the prerequisite for generics, interfaces, externref-DOM, and events alike. P1 (TLSF + dyn arrays) runs in parallel as the memory spine; P3–P5 are additive emitter work on the proven layout engine (with P5-OPT honestly L/high because the multi-return rvar machinery must grow, and a new P5-STRMETH milestone for the string methods the parser actually needs); externref must get its **own** `is_reftype` predicate and live in a reference **table**, never linear memory (folding it into `is_pure_type` is a correctness bug). WasmGC (P6) is deliberately last and deliberately optional: it is a multi-month, parallel memory model — a second backend, not a milestone — that buys cyclic-graph collection only when both guest and host drop their references. **The single highest-leverage first move is P2's table/element writer + `call_indirect` (after the harness is in place to prove it actually runs, not merely validates).**
