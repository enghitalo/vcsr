# vcsr project review — October 2026

A whole-project review taken right after vcsr was brought up to date with the
rewritten V compiler (v3) and the latest vanilla (PRs #11, #12). Every claim
below was checked by reading the code **and** running it: `make test`, the
`vcsr` CLI, `vcsr wasm` with wasi-sdk-34 / clang 23, and real Chrome through
Playwright. The follow-up work is tracked in [ROADMAP.md](ROADMAP.md).

## What renders today

V source → `vcsr gen` → `vcsr wasm` → Chrome, checked feature by feature with a
probe component:

| Template feature | Renders? | Notes |
|---|---|---|
| `{{ expr }}` as an element's only child | ✅ | reactive |
| computed methods (`{{ doubled }}`) | ✅ | called, re-run on signal writes |
| `:attr="expr"` | ✅ | reactive |
| `@click="method"`, `@click="method(args)"` | ✅ | no event payload |
| `@bind="sig"` on `Signal[string]` | ✅ | `value` + `input` only |
| `@if` | ❌ | content never rendered; toggles the **parent's** visibility |
| `@for` | ❌ | no rows; sets `data-count` only (both backends) |
| `class:name="expr"` | ❌ | parsed, then silently dropped |
| child components / props | ❌ | emitted as an unknown `<badge>` element |
| text mixed with `{{ }}` in one element | ❌ | compile error |
| void tags without `/>` (`<input>`) | ❌ | parse error |
| component CSS | ❌ | `style()` never injected on wasm; scoped names don't match the markup |

`testdata/dashboard-app` and `testdata/fixture-app` also render in Chrome
(14/14 and 18/18 checks), but their wasm is **hand-written** C and WAT — they
exercise the bundler, loader and serving, not the compiler. The only app that
goes V → vcsr → wasm is `examples/counter`.

## Good — keep

- **The core model.** Clone-and-patch from an embedded HTML skeleton plus a
  slot table, driven by fine-grained signals with dynamic dependency tracking
  and disposal ([signal.v](../signal.v)). It is closure-free by construction,
  which is exactly what makes it run on wasm.
- **The two-backend runtime.** The native mock DOM and the wasm host-DOM backend
  share one API, so the generated `view()` compiles unchanged against both.
- **No V compiler changes.** Codegen emits plain V; the triplet model
  (`.v` + `.html` + `.css`) keeps logic, markup and styles in separate files.
- **The bundle/serving layer.** Content hashing, write-if-changed + pruning,
  gzip/brotli siblings, and the contract with vanilla's `static_assets`
  (application/wasm, encoding negotiation, immutable caching, SPA fallback) are
  real and verified against vanilla itself.
- **The wasm byte reader** (`wasm.inspect`) — small, bounds-checked, useful for
  checking real output.
- **Tests with real signal:** phases 01–03 (pure passes), 12 (signals), the
  vanilla serving checks in 09/10, byte inspection in 11.

## Bad — bugs and gaps

**Template language** (parser / slots / bind)

- Text is scanned up to the next `<`, so `{{ a < b }}` fails; pretty-printed
  templates break (`<p>\n {{ x }}\n</p>` is "mixed content"); content after
  the root is silently dropped; void elements need `/>`; attribute values are
  re-quoted unescaped (`title='say "hi"'` → broken HTML); `<span/>` on a
  non-void element emits no closing tag, shifting every later slot path.
- `bind.free_idents` mis-tokenizes numbers (`1e5` → `e5`), escapes, `${}` and
  keywords (`in`, `if`, `int(x)` become "unknown references").
- `@if`/`@for`/`class:` are compiled into slot descriptors the runtime cannot
  act on (see the table above).

**Styles**

- Two scopers disagree (`component.scope_css` vs `css.scope`); neither rewrites
  the template's class names, so scoped CSS never matches the markup.
- `css` breaks on comments, strings, `url()`, block-less and nested at-rules,
  `@keyframes`/`@font-face`; selectors are over-scoped (`[href$=".pdf"]`).
- `atomize` merges rules across the cascade and **changes which rule wins**
  (`.a{red} .b{blue} .c{red}` → `class="b c"` flips colour).

**Host / loader**

- Four host loaders, two live and mutually incompatible: `bundle.loader_js()`
  (WAT fixture ABI) and `cmd/vcsr/templates/wasm_loader.js` (`host_*`, the one
  V output needs); plus a copy in `examples/counter/wasm/app.js`, the
  dashboard's `el_*` ABI, and a Node re-implementation in `dom.mjs`.
- The DOM ABI's JavaScript lives in the *user-editable* `app.js` that
  `vcsr wasm` never overwrites — so every new host import breaks existing apps.
- `host_on` calls `preventDefault()` on every cancelable event (links and
  checkboxes break), while the parsed `.prevent` modifier is ignored.

**Build pipeline — modelled, not real**

- `vcsr build` only bundles **prebuilt** wasm; there is no path from V
  component sources to a `dist/`. Its loader can't load V output, and its
  `index.html` has no `#app` mount point.
- Code splitting, the link plan, dead-route elimination, prefetch hints and
  `wasm-opt` levels are computed over metadata and never applied. The link plan
  is hard-coded constants; `verify_abi` rejects every real V module; route
  chunks are emitted but never loaded; the source map is a stub at a URL that
  404s.
- The fixture wasm files are **hash-mined** (a nonce section) so their content
  hashes match values the tests hard-code; recompiling them breaks the tests.

**Tests that give false confidence**

- Phase 07 asserts a hand-filled struct; phase 10's "dead-route elimination" and
  "no WASI imports" pass only because of how the fixtures were made; phase 14
  asserts the `data-count` stub and a hand-written `@if` shape; phase 04 asserts
  the *unscoped* `class="counter"`, enforcing the scoping bug.
- `counter_test.v` runs against the committed `counter.gen.v`, so a codegen
  regression doesn't fail it.
- No V-built wasm is exercised by `make test`.

**Docs**

- About nine places still say V can't emit browser wasm; phase tables mark
  modelled features ✅; generated-code samples are from an older codegen; size
  numbers are from older V (the counter is ~205 KB on v3, docs say 82–165 KB);
  the documented ABI (`mount(externref)`, `__v_alloc`) isn't the one that ships
  (`runtime/vcsr_host.h`), which is documented nowhere.

## Rework — duplication and dead weight

- **Duplicated code:** `free_idents` ≡ `component.qualify` (same tokenizer, same
  bugs); `is_ident_*`/`is_space`/`index_of`/`scope_token` copied across 3–4
  modules; glob matching and wasm LEB128 parsing duplicated between `bundle`
  and `manifest`/`wasm`; three "last path segment" helpers that disagree;
  `content_type_of`/`cache_policy` re-implement vanilla's and have drifted.
- **Computed but never consumed:** `bind.BindingPlan`, `css.atomize_with_usage`
  (tree-shaking), `ScopedCss.renames`, the router plan, `wasm.link`.
- **Two runtime binding APIs** (closure `bind_*` for hand-written tests vs
  closure-free `bind_*_ctx` that codegen emits); tests mostly cover the former.
- **CLI as shell strings:** the V→wasm recipe lives in `cmd/vcsr` and is
  copy-pasted into two `build.sh` scripts instead of being a library call.
- **Docs overlap:** the triplet is explained four times, `dist/` twice, the
  V→wasm status in ~9 places (which is why they drift).

## V v3 issues found (worked around in vcsr)

1. Pushing a `mut x T` param into `[]&T` inside a generic method instantiated
   cross-module memdups the pointer variable (garbage copy).
2. Imports resolve against the main program's project root for *every*
   importing file — a dependency's `import runtime` binds to the project's own
   `runtime/` dir.
3. `$embed_file(..)` is rejected as a direct call argument.
4. A value `__global` whose struct field defaults to a selectively-imported
   generic fn makes `_vinit` emit an undeclared C call.
5. The C preamble includes POSIX headers WASI lacks; `-arch` isn't implied for
   wasm targets (x86 inline asm leaks in).
6. `vmemcpy`/`vmemmove`/`vmemset`/`vmemcmp` treat pointers `<= 0xFFFF` as null
   and silently do nothing — wrong on wasm32, where memory starts at 0.
