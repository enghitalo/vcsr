# Example: counter

The smallest meaningful vcsr app: a single component as a **file triplet** — V
logic, an HTML template, and CSS in separate files. The page ships empty; the
WASM builds the UI client-side and patches only the text nodes that change.

```sh
vcsr build ./src --out dist --release
# serve dist/ — see ../serve-with-vanilla
```

Files:

- [src/counter.v](src/counter.v) — **logic**: the `Counter` struct, its `count`
  signal, the `inc` handler, and the `doubled` computed. No `view()`/`style()` —
  vcsr generates those.
- [src/counter.html](src/counter.html) — the **template** (vcsr's dialect).
- [src/counter.css](src/counter.css) — **scoped styles**.
- [src/main.v](src/main.v) — the app entrypoint (`new_app` → `render` → `mount`).
- [index.html](index.html) — the empty shell; `vcsr build` emits the hashed
  production version into `dist/`.

What to notice:

- `{{ count }}` and `{{ doubled }}` are the only dynamic holes; `@click="inc"`
  binds the handler. These identifiers resolve in the `Counter` struct's scope.
- A click runs `inc`, which calls `count.update(...)`; only the two text nodes
  that read those signals update — no re-render, no diff.
- vcsr scopes `counter.css` to `Counter` at build time, so `.counter`/`.muted`
  can't collide with any other component.
- vcsr generates `counter.gen.v` (plain V) implementing `view()`/`style()`;
  stock `v` compiles it. **No `$vui`/`$css`, no V compiler changes** — see
  [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md).

## What vcsr generates (real output)

This triplet runs through the **implemented** pipeline today — `parser` → `slots`
→ `bind` → `component` codegen + `css` scoping. Feeding `counter.{v,html,css}` to
`component.analyze(...).codegen()` produces `counter.gen.v`:

```v
// counter.gen.v — GENERATED by vcsr. Do not edit. (excerpt)
module main

import vcsr.runtime

const __counter_tpl = runtime.Template{
	html:  '<main class="counter"><h1></h1><p class="muted">double <span></span></p><button>+1</button></main>'
	slots: [
		runtime.SlotDesc{ kind: .text,  path: [0] },     // <h1>      ← count
		runtime.SlotDesc{ kind: .text,  path: [1, 0] },  // <span>    ← doubled
		runtime.SlotDesc{ kind: .event, path: [2], name: 'click' }, // <button> ← inc
	]
}

pub fn (mut c Counter) view() vcsr.View {
	mut ins := __counter_tpl.instance()
	runtime.bind_text(mut ins, 0, fn [c] () string { return runtime.to_str(c.count.get()) })
	runtime.bind_text(mut ins, 1, fn [c] () string { return runtime.to_str(c.doubled()) })
	runtime.bind_event(mut ins, 2, c.inc)
	return ins.view()
}
```

The static HTML is the skeleton (every dynamic hole emptied) and lives verbatim
in the wasm data segment; the slot table says exactly which node each signal
patches. `c.count.get()` reads the signal; `c.doubled()` calls the computed; the
`<span>` wrapper keeps `{{ doubled }}` as an element's sole child (what the slot
extractor supports today). `counter.css` is scoped to a per-component hash so
`.counter`/`.muted` can't collide. The only thing missing to *run* this is the
`vcsr.runtime` library + browser-wasm emission (roadmap).
